# Diabetic Retinopathy MLOps Pipeline

End-to-end ML cycle for **5-class diabetic retinopathy grading** from retinal fundus images (non-tabular), with FastAPI serving, Streamlit UI, SQLite-backed upload → preprocess → retrain, Docker scaling, and Locust load tests.

Bridges the Intro-to-ML summative (diabetic patient outcomes) into an **image** clinical screening use case.

## Datasets

Two public fundus datasets, both graded on the same 5-level ICDR scale:
**`0 No_DR`, `1 Mild`, `2 Moderate`, `3 Severe`, `4 Proliferate_DR`**.

| Dataset | Images | Source | Role |
|---------|--------|--------|------|
| **APTOS 2019** | 3,662 (224×224) | HF mirror `bumbledeep/aptos` of [Diabetic Retinopathy 224×224 Gaussian Filtered (Kaggle)](https://www.kaggle.com/datasets/sovitrath/diabetic-retinopathy-224x224-gaussian-filtered) | Primary dataset: training + the main held-out test set |
| **EyePACS** | 35,108 (~1024px) | Hugging Face [`ctmedtech/EYEPACS`](https://huggingface.co/datasets/ctmedtech/EYEPACS) (`EYEPACS.zip` + `trainLabels.csv`), a re-host of the labelled training set from Kaggle's 2015 [*Diabetic Retinopathy Detection*](https://www.kaggle.com/c/diabetic-retinopathy-detection) | Extra training data from different cameras/clinics + a second held-out test set |

The full split (85/15 per class for APTOS; patient-level 85/15 for EyePACS so a person's left and right eye never straddle train/test), the folder layout, and exactly which images were used for what are documented in **[`data/README.md`](data/README.md)**. Gaussian filtering is applied in `src/preprocessing.py` to every image at train and predict time.

**Citations**

- APTOS: Karthik, Maggie, and Sohier Dane. *APTOS 2019 Blindness Detection*. Kaggle.
- EyePACS (as requested by the dataset card): Kaggle and EyePACS. "Diabetic Retinopathy Detection." Kaggle Competition, 2015. https://www.kaggle.com/c/diabetic-retinopathy-detection. Accessed via Hugging Face: [`ctmedtech/EYEPACS`](https://huggingface.co/datasets/ctmedtech/EYEPACS).

**License note:** the EyePACS dataset card says use is restricted under Kaggle and EyePACS terms, and redistribution may be restricted. This repo does **not** include any EyePACS images (`data/raw/` and `data/splits/` are gitignored). Anyone reproducing the results downloads EyePACS themselves under those terms.

## Setup

```bash
cd mlp-summative
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 1) Download APTOS into data/raw/aptos/ (+ small demo samples in data/samples/)
python scripts/download_data.py

# 2) EyePACS (manual): download EYEPACS.zip + trainLabels.csv from
#    https://huggingface.co/datasets/ctmedtech/EYEPACS, unzip the images into
#    data/raw/eyepacs/images/ and put trainLabels.csv in data/raw/eyepacs/

# 3) Build the train/test splits in data/splits/ (deterministic, seed 42)
python scripts/build_combined.py

# 4) Train the deployed model and score it on the held-out test sets:
#    run notebook/diabetic_retinopathy.ipynb top to bottom (saves models/*.h5 + metrics.json)
jupyter nbconvert --to notebook --execute --inplace notebook/diabetic_retinopathy.ipynb \
    --ExecutePreprocessor.timeout=-1
#    (same recipe as a script: python scripts/train_model.py --data data/splits/mixed_train \
#     --augment --epochs-head 10 --epochs-ft 20 --patience 6)

# 5) Run API + UI locally
uvicorn api.main:app --reload --port 8000
# other terminal
API_URL=http://localhost:8000 streamlit run ui/app.py
```

| Locust flood + multi-container latency | `locust/` + table below |

### Retrain trigger chain

1. Upload images → saved to SQLite + `data/uploads/`
2. Preprocess (resize, Gaussian, normalize)
3. Fine-tune starting from **your** saved MobileNetV2 checkpoint as pretrained weights
4. Save over `models/diabetic_retinopathy_mobilenet.h5`, keeping the previous model as `diabetic_retinopathy_mobilenet.h5.bak`

If a retrain makes predictions worse, **Restore backup model** in the Retrain tab (`POST /reset-model`) deletes the current `.h5` and renames the `.bak` back to `.h5`. This undoes one retrain; `GET /health` reports `backup_available`. The original trained model can always be restored from git: `git checkout models/diabetic_retinopathy_mobilenet.h5`.

## Flood request simulation (Locust)

```bash
mkdir -p locust_results
# with the stack up: same load against 1, 2 and 3 API containers
scripts/run_locust_scaling.sh 30 60s
# single run against whatever is running:
docker compose --profile load run --rm --no-deps locust
# or from the venv:
locust -f locust/locustfile.py --host http://localhost:8000 --headless -u 30 -r 10 -t 60s --csv locust_results/out
```

`--no-deps` matters: without it, `docker compose run` re-applies the default scale and silently drops the extra API replicas.

### Results: hosted version (AWS EC2)

Run on the deployed instance (`c7i-flex.large`: 2 vCPU, 4 GB RAM) with `scripts/run_locust_scaling.sh 30 60s`. Locust floods `POST /predict` through nginx (`least_conn` load balancing) with **30 concurrent users for 60 s** per setting. Each user waits 0.1–0.5 s between requests:

| API containers | Requests | Throughput (req/s) | Median latency | Avg latency | p95 latency | p99 latency | Failures |
|----------------|---------:|-------------------:|---------------:|------------:|------------:|------------:|---------:|
| 1 | 908 | 15.4 | 1,600 ms | 1,601 ms | 1,800 ms | 1,800 ms | 0 |
| 2 | 1,097 | **18.6** | **1,300 ms** | **1,275 ms** | **1,500 ms** | 1,600 ms | 0 |
| 3 | 1,091 | 18.4 | 1,300 ms | 1,281 ms | 1,600 ms | 1,800 ms | 0 |

nginx spread requests evenly (2 containers: 560 / 554; 3 containers: 371 / 379 / 358). There were **no failed requests** in any run, even though 30 users kept the server fully loaded throughout.

- **1 → 2 containers:** throughput +21 %, median latency −19 %. One container handles one prediction at a time, so it leaves the instance's second vCPU mostly idle. A second container puts it to work.
- **2 → 3 containers: no further gain.** With 2 vCPUs, two containers already use all the CPU, so a third one only splits the same CPU time. Scaling further on AWS would need a bigger instance or more instances behind a load balancer, not more containers on this one.
- Latency is mostly queueing: at 30 users, each request waits behind the others.

### Results: local machine (for comparison)

The same script on a MacBook (12 CPUs, 8 GB for Docker). With more cores, every added container gets its own CPU, so scaling continues to 3 containers:

| API containers | Requests | Throughput (req/s) | Median latency | Avg latency | p95 latency | p99 latency | Failures |
|----------------|---------:|-------------------:|---------------:|------------:|------------:|------------:|---------:|
| 1 | 1,676 | 28.4 | 750 ms | 736 ms | 840 ms | 880 ms | 0 |
| 2 | 3,077 | 52.1 | 270 ms | 269 ms | 370 ms | 410 ms | 0 |
| 3 | 4,196 | **71.0** | **110 ms** | **115 ms** | **210 ms** | **250 ms** | 0 |

Going from 1 to 3 containers gives 2.5× the throughput and ~7× lower median latency. Comparing the two machines shows that adding containers helps only while there are idle CPU cores for them.

Raw CSVs: `locust_results/ec2_api{1,2,3}_stats.csv` (EC2) and `locust_results/api{1,2,3}_stats.csv` (local).

## Model

**Deployed:** MobileNetV2 (ImageNet weights), fine-tuned on **all APTOS training images + 2,000 EyePACS images (400 per class)**, with train-time augmentation (random flips, full rotation, ±10 % zoom, brightness/contrast) — 10 frozen-backbone epochs + 20 fine-tune epochs, early-stopping patience 6. Trained on `data/splits/mixed_train` (5,112 images, 20 % held out for validation).

The model is **created in [`notebook/diabetic_retinopathy.ipynb`](notebook/diabetic_retinopathy.ipynb)**. It covers data acquisition, preprocessing (with before/after images), augmentation, class weights, the model and its optimization techniques, training curves, evaluation on the held-out test sets, and the prediction function. It saves `models/diabetic_retinopathy_mobilenet.h5` and `models/metrics.json`. Training takes about 9 minutes on a laptop CPU.

### Held-out test results

Scored on images **never used for training or validation** (from `models/metrics.json`):

| Test set | Images | Accuracy | Loss | Precision (macro) | Recall (macro) | **F1 (macro)** |
|----------|--------|----------|------|-------------------|----------------|----------------|
| APTOS test | 550 | **0.751** | 0.645 | 0.582 | 0.571 | **0.568** |
| EyePACS test (other cameras) | 300 | 0.423 | 1.403 | 0.372 | 0.423 | 0.370 |

Per-class F1:

| Test set | No_DR | Mild | Moderate | Severe | Proliferate_DR |
|----------|-------|------|----------|--------|----------------|
| APTOS | 0.97 | 0.55 | 0.63 | 0.27 | 0.42 |
| EyePACS | 0.25 | 0.45 | 0.00 | 0.51 | 0.64 |

The model reliably separates healthy eyes from diseased ones: only 12 of 279 diseased APTOS test images are predicted No_DR. Most errors are between neighbouring grades. 15 of 29 Severe images are predicted Moderate (still a "refer to specialist" grade in DR screening), and Proliferate_DR is often called Severe. Severe has just 29 APTOS test images, so its score is noisy. On EyePACS photos the model handles Severe and Proliferate_DR well, but it calls most No_DR and Moderate images Mild. That gap between cameras is what retraining with uploaded EyePACS-style images is meant to close.

### How it compares with earlier models

Scored on the same held-out test images:

| Model | APTOS accuracy | APTOS F1 | EyePACS accuracy | EyePACS F1 |
|---|---|---|---|---|
| Same recipe, trained by `scripts/train_model.py` (deployed before the notebook run; kept as `models/experiments/deployed_before_notebook.h5`) | 0.745 | 0.543 | 0.420 | 0.369 |
| **Notebook run (deployed)** | **0.751** | **0.568** | **0.423** | **0.370** |

The difference is within run-to-run noise. Both are clearly better than the first model (APTOS only, 400 images per class, no augmentation). That model's README reported F1 ≈ 0.60, but the number was inflated: its validation images were reused for testing, and many of the old `data/test` images were in its training set. On fair, unseen EyePACS test images it scored 0.263 accuracy / 0.185 F1.

### Experiments

All models scored on the same held-out test sets (`scripts/evaluate.py`):

| Training data | Augment | Epochs (max) | APTOS F1 | EyePACS F1 |
|---------------|---------|--------------|----------|------------|
| APTOS, 400/class (previous recipe) | – | 10 | 0.513 | 0.177 |
| APTOS, all | – | 20 | 0.538 | 0.172 |
| APTOS, all | ✓ | 30 | 0.451 | 0.136 |
| APTOS + EyePACS, 400/class | – | 10 | 0.501 | 0.309 |
| APTOS all + EyePACS | – | 20 | 0.520 | 0.329 |
| **APTOS all + EyePACS (chosen recipe)** | ✓ | 30 | **0.543** | **0.369** |

Findings: using all APTOS images helps; EyePACS only pays off with augmentation and a longer training budget, after which it matches the best APTOS-only model on APTOS while doubling performance on images from other cameras. Single training run per setting, so differences under ~0.02 F1 are within noise.

> `models/metrics.json` is written by the notebook and holds the held-out **test** results above. Training with `scripts/train_model.py` instead overwrites it with **validation** metrics.

## Deploy on AWS (EC2 + Docker Compose)

The whole Compose stack (api + nginx + ui) runs on a single EC2 instance, so the SQLite DB, uploads, and retrained models persist on the instance's EBS volume.

| Piece | Setting |
|-------|---------|
| Instance | `c7i-flex.large` (2 vCPU, 4 GB) + 4 GB swap, Amazon Linux 2023 |
| Disk | 30 GB gp3, encrypted |
| Network | Default VPC, public IP; security group opens **8000** (API) and **8501** (UI) only — no SSH |

Bootstrap: [`scripts/ec2-user-data.sh`](scripts/ec2-user-data.sh) is passed as EC2 user data. It adds swap, installs Docker + Compose/buildx, clones this repo to `/opt/app`, writes a `docker-compose.override.yml` with `restart: unless-stopped`, then runs `docker compose build && docker compose up -d`. First boot takes ~5 min (TensorFlow image build); log at `/var/log/app-bootstrap.log`.

Run:

```bash
# shell on the instance (no SSH key needed)
aws ssm start-session --target <instance-id> --region eu-north-1

# on the instance
cd /opt/app
sudo git pull && sudo docker compose up -d --build   # deploy latest code
sudo docker compose up -d --scale api=2              # scale API replicas behind nginx
sudo docker compose logs -f api
```

Notes:

- `/upload` and `/retrain` are unauthenticated and publicly reachable; restrict the security group to known IPs when not demoing.
- Stop the instance between demos to save cost (~$0.08/hr running); data on the EBS volume is kept, but the public IP changes.

## API quick reference

- `GET /health` — uptime + model status  
- `POST /predict` — multipart `file`  
- `POST /upload` — multipart `files` + form `labels` (`0,1,2,...`)  
- `POST /retrain` — JSON `{ "epochs": 3 }`  
- `POST /reset-model` — undo the last retrain (restore `.h5.bak`)  
- `GET /insights` — chart data + interpretations
